# 커밋 가이드 

## 규칙 

커밋 메세지의 규칙은 다음과 같다. 

### subject

`{prefix}: {title}` 

prefix는 아래의 카테고리를 사용한다. 
- feat: 기능 개발/변경
- fix: 동작에 문제가 발생하여 수정
- chore: ci/cd 또는 빌드, package install 등 앱 인프라 변경점
- docs: 문서 업데이트

title은 작업에 대한 전체 요약을 80자 이내로 작성한다. 현재 수행한 작업이 무엇을 위한 작업인지 작성한다. 
`예시) User 서버 상태를 전역 상태로 접근하기 위한 Provider 설정`
꼭 예시와 같은 형식은 아니어도 원인과 결과의 형태로 최대한 작성을 지향한다.

### body

생략이 가능하며, 어떤 작업이 수행되었는지 요약하여 작성한다.

## 커밋 절차

1. 작업하는 디렉토리의 베이스에서 브랜치까지 작업의 히스토리를 커밋 기록으로 확인한다. 
2. 작업하는 디렉토리 기준으로 작업 변경 사항을 파악한다. 
3. 작업 내용이 연관성있는 작업으로 동작하는 단위로 stage로 묶어 커밋을 수행한다. 
4. 변경점이 없을때 까지 작성을 수행한다. 


## pre commit

작업한 프로젝트에서 pre commit 에서 lint/format/test를 실행하여 검증이 진행이 될 수 있다. 해당 검증은 특별한 경우가 아니면 통과하는것을 목표로 한다. 

### lint/format

만약 작업한 코드가 아닌 다른 부분에서 발생했다면, 간단하게 수정이 가능하면 수정을 함께 진행한다. 만약 그렇지 않고 구조적인 변경이 필요하면 작업한 코드에 대한 검증이 없다면 --no-verify 로 스킵힌다. 

typescript에 대해서 타입 에러가 발생하는 경우 any, unkwon, as 등 에러를 당장 안뜨는 방향의 수정은 최대한 수행하지 않는다. 근본적인 타입의 문제를 수정하고 나와 논의하여 결정이 필요한 경우 커밋을 멈추로 논의하고 작업을 수행한다. 

### test

테스트는 all pass 를 최대한 도달하고자 한다. 실패하는 경우 실패의 원인을 분석하고 현재 작업에 대해서 발생 이유를 요약해서 제시한다. 

테스트 코드는 프로젝트에 작성된 코드의 정합성을 검증할 수 있어야한다. 변경에 따라 테스트 코드가 잘못 작성되었다면 테스트 코드를 최신화한다. 만약 테스트 코드가 제대된 검증으로 작성되었는데 검증 대상 코드가 잘못되었다면 잘못된 부분을 파악하여 나에게 제시해줘. 이를 토대로 작업 방향을 결정한다.

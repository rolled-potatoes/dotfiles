# 완료된 개발 워크트리 정리

## 대상과 정리 가능 여부 확인

- 사용자 요청의 작업·PR·브랜치와 `list_artifacts` 및 `git worktree list --porcelain`의 저장소·경로·브랜치·HEAD를 대조한다. 대상이 모호하면 후보를 보여 주고 확인한다. 기본 체크아웃과 진행 중인 다른 작업의 워크트리는 정리 대상에서 제외한다.
- 작업이 반영되어야 할 대상 브랜치를 확인한다. 최신 기준 브랜치의 이력에 워크트리 HEAD가 포함되는지 확인하거나, squash·rebase 병합이라면 해당 PR의 병합 상태와 병합 당시 소스 HEAD를 현재 HEAD와 대조한다. 운영 브랜치와 `develop` 모두에 반영해야 하는 작업은 두 곳을 확인한다. 근거가 부족하거나 병합 이후 추가 커밋이 있으면 정리를 보류한다.
- 대상에서 `git status --short --untracked-files=all`을 확인한다. 미커밋 변경이나 미추적 파일이 있으면 필요한 내용을 보존할 방법을 확인할 때까지 보류한다. `git status --short --ignored=matching`으로 제거되거나 보관에서 빠질 수 있는 무시 파일을 확인한다. 필요한 로컬 설정이나 자료가 있으면 먼저 보존한다. 파일 내용이나 비밀값을 출력할 필요는 없다.

## 정리 및 확인

- 정리 후보를 묻는 요청에는 경로, 브랜치, 반영 근거, 보류 사유를 보고한다. 정리 실행은 사용자 요청이나 승인으로 범위가 확정된 대상에 한한다. 실행 직전에 대상과 HEAD, 파일 상태를 다시 확인한다.
- Codex 관리 워크트리는 `list_artifacts`의 정확한 워크트리 식별자로 `archive_worktree`를 호출한다. 보관이 거절되면 사유를 보고한다. Git 명령으로 우회하면 Codex에서 복구할 수 없으므로 관리 워크트리는 보관 도구로만 정리한다.
- 일반 Git 워크트리는 같은 저장소의 남겨 둘 체크아웃에서 `git worktree remove -- "<워크트리 경로>"`를 실행한다. Git이 제거를 거부하면 사유를 확인하고 보류한다. 강제 제거, 디렉터리 직접 삭제, 일괄 정리는 사용하지 않는다.
- 워크트리 정리 범위는 체크아웃 경로에 한정한다. 브랜치 삭제는 별도 요청 범위에서 다룬다.
- Git 워크트리 목록에서 대상이 빠졌는지 확인한다. Codex 관리 워크트리는 보관 목록에도 있는지 확인한다. 처리 결과와 남은 보류 사유를 보고한다.

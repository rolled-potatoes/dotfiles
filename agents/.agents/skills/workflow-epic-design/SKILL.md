# 업무 설계

기획을 현재 프로젝트의 도메인과 연결해, 구현자가 상세 계약을 설계할 수 있는 방향 기술 설계서와 epic 초안을 만든다. 상세 API, ENUM, 스키마는 `$workflow-story-design`에서 다룬다.

먼저 저장소 지침과 Git 상태를 확인하고 `explorer`에게 기존 도메인, 용어, 경계, 구현 근거를 조사시킨다. 도메인 모델이나 경계가 핵심이면 책임, 규칙, 상태, 다른 도메인 영향을 근거와 함께 정리한다. 업무툴 원문은 실제로 읽고 source key·링크·수정 시각을 기록한다.

사용자와 아이디어를 조합해 후보를 만들고, 책임 경계·규칙·호환성·운영·이행 영향을 비교한다. 선택에 따라 의미나 계약이 달라지는 쟁점만 2~3개 선택지와 권장안을 제시해 논의한다. 일정, 정책, 상세 구현을 근거 없이 채우지 않는다.

승인 전 기술 설계서는 다음을 포함한다.

- 배경·목적, 목표·범위·제외
- use case, 책임과 도메인 경계, 방향과 규칙
- 선택 이유와 선택하지 않은 대안의 이유
- 운영·이행 영향, 미결정 항목
- 적용할 story/task와 확인 기준

epic 초안에는 목표, 범위, 일정에 대해 확인된 사실만, 그리고 기술 설계서 링크를 포함한다. 외부 기록은 공통 규칙의 승인 경계를 지킨다.

공통 권한·기록·완료 규칙은 [development-workflow.md](../../references/development-workflow.md)를 읽고 따른다.

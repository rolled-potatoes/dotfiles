# 개발 시작

## 작업과 반영 대상 확인

- 승인된 기획·티켓과 사용자 요청에서 작업 유형, 식별자, 대상 저장소를 확인한다. 여러 저장소를 수정하면 각 저장소에 이 절차를 적용한다.
- 기능 개발은 기준 원격의 최신 `develop`에서 분기하고 `develop`으로 PR을 연다. 버그 수정은 기준 원격의 최신 운영 브랜치에서 분기하고, 운영 브랜치에 먼저 병합한 뒤 같은 수정을 `develop`에도 반영한다.
- 운영 브랜치는 사용자 지정이나 저장소의 브랜치 운영 지침을 따른다. 명시된 기준이 없으면 운영 배포 설정과 최근 운영 버그 수정 PR의 병합 대상을 확인한다. `main`·`master`라는 이름이나 원격 기본 브랜치는 참고 정보로만 사용한다. 근거가 엇갈리거나 작업 유형·기준 원격·분기점을 특정하기 어려우면 결정에 필요한 항목만 묻는다.
- 새 브랜치 이름은 저장소 규칙을 따른다. 별도 규칙이 없으면 기능은 `feature/<작업 식별자>`, 버그는 `hotfix/<작업 식별자>`를 사용한다.

## 기존 작업 재개

- 연결된 워크트리, `git worktree list --porcelain`, 로컬·원격 작업 브랜치를 확인한다. 같은 저장소와 작업의 별도 워크트리가 있으면 경로·브랜치·변경 상태를 확인하고 그곳에서 이어간다.
- 작업 브랜치만 남아 있으면 해당 브랜치를 별도 워크트리에 체크아웃한다. 원격에만 있으면 해당 원격 작업 브랜치를 추적하는 로컬 브랜치를 사용한다. 재개할 때는 기존 커밋과 미커밋 변경을 보존하고, 기준 브랜치와의 동기화는 별도로 판단한다.

## 새 작업 준비

- 확정한 원격의 기준 브랜치를 fetch하고 가져온 커밋 SHA를 확인한다. fetch에 실패하면 원인을 해결한 뒤 분기한다. 원래 저장소의 체크아웃과 미커밋 변경은 그대로 둔다.
- Codex 앱에서는 워크트리 생성 도구의 실제 입력을 확인하고 기준 SHA로 워크트리를 만든다. 완료 후 반환된 경로에서 작업 브랜치를 생성한다. CLI에서는 `git worktree add -b <작업 브랜치> <경로> <기준 SHA>`를 사용한다.

## 첫 수정 전 확인

- 실제 작업 경로에서 저장소 루트, 현재 브랜치, HEAD를 다시 조회한다. 새 작업이면 HEAD가 가져온 기준 SHA와 일치하는지, 재개라면 기존 작업 브랜치에 체크아웃되어 있는지 확인한다.
- 확인한 작업 브랜치와 워크트리 경로를 짧게 알리고 그 경로에서 구현·테스트한다. 원격 반영 요청 시 확정한 반영 대상을 인계한다. 커밋·push·PR·병합·워크트리 삭제에는 기존 승인 절차를 적용한다.

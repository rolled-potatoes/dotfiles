# Story·작업 설계

승인된 epic과 방향 기술 설계서를 독립적으로 수행 가능한 story 또는 작업으로 나눈다. 시작할 때 다음 두 경로 중 하나를 고른다.

- **직접 구현**: 본인이 story 개발을 맡는다. 상세 spec을 구성하고, 실행 action item을 Jira 하위 태스크로 생성·기록·구현한다.
- **위임 계약**: 다른 엔지니어에게 개발을 위임한다. 범위와 인수조건 중심의 story를 전달하고, 상세 spec과 실행 하위 태스크는 수임자가 작성한다.

사용자의 명시, 이미 알려진 담당, 요청 목적에서 경로를 판단한다. 정보가 부족할 때만 한 번 간결히 묻고, 테크리더라는 직함만으로 위임을 추정하지 않는다.

원천 epic과 최신 프로젝트 근거를 다시 확인한다. 같은 완료조건을 공유하는 server·client 작업을 형식적으로 분리하지 않는다. 각 story는 책임·변경 범위·의존성·완료조건이 분명한 계약이어야 한다.

두 경로의 story에는 다음 공통 계약을 포함한다.

- 목표, 범위와 제외 범위
- 검증 가능한 인수조건, 상위 epic link
- 이미 확정된 제약과 의존관계

직접 구현 경로에만 인수조건과 다음 상세 설계를 포함한다.

- API의 parameter·response·error, 필요한 ENUM·schema·migration
- 별도 배포 시스템의 wire compatibility와 프로젝트별 책임 경계
- 각 인수조건과 단위·통합·E2E 등 검증 근거의 명확한 연결
- 위험, 호환성, 미결정 사항과 사람 검토가 필요한 선택

## 직접 구현의 하위 태스크 생성 게이트

story의 진행 상태를 다음 순서로 구분해 보고한다.

1. **설계 초안** — story와 하위 태스크 계획만 있다.
2. **사람 검토** — 인수조건과 상세 계획을 검토·수정한다.
3. **Jira 반영 승인 대기** — 생성할 목록·대상 parent·내용·예상 영향을 검토 가능하게 준비한다.
4. **실제 생성·readback** — 승인 뒤 Jira에서 child를 만들고 parent·type·내용을 다시 확인한다.
5. **구현 준비 완료** — 승인 목록과 실제 child, parent 연결, 필요한 내용과 인계가 모두 확인됐다.

사용자가 draft-only를 지시하면 1~3에서 멈추고 `초안/승인 대기`로 표시한다. 계획 검토 승인은 외부 생성 승인과 다르다. 다만 승인에 생성 행동·parent·대상 목록·범위가 포함되면 같은 범위를 다시 묻지 않는다. 초안을 준비한 뒤 생성 승인을 구체적으로 요청하며, 누락을 단순 후속 작업으로 미루고 종료하지 않는다. 이 생성 게이트는 직접 구현 경로에만 적용한다.

각 구현 단위에는 아래 형식의 복사 가능한 최소 설명을 만든다. 담당자나 일정은 근거 없이 넣지 않고, story 본문 전체를 복제하는 대신 실행에 충분한 요약과 canonical link를 쓴다.

```md
부모 story: <key> — <canonical link>

목표와 결과물
- <완료 시 제공할 결과>

범위
- 포함: <변경 대상>
- 제외: <이 작업에서 하지 않을 것>

인수조건과 완료조건
- 부모 AC: <AC ID 또는 canonical link>
- 이 하위 태스크 완료조건: <검증 가능한 조건>

구현 방향
- 대상: <repository/component>
- 상세 계약·설계: <canonical link>

검증
- 방법과 예상 결과: <test/build/lint 등>

의존성 및 순서
- 선행 하위 태스크: <key 또는 없음>
```

실제 생성 전에는 도구에서 issue type의 subtask 여부, parent 지정 지원, required field를 조회하고 명칭·ID·필수 필드를 가정하지 않는다. 메인은 승인 뒤 parent story를 지정해 생성한다. 먼저 기존 children을 조회해 중복을 막는다. 부분 성공 또는 timeout이면 현재 Jira를 key별로 다시 조회해 reconcile하며, 성공분은 재생성하지 않는다. 이름만 같은 child는 자동으로 동일하다고 단정하지 말고 모호성을 확인한다.

생성 뒤에는 각 child를 GET하여 key·parent·type·description·AC를 확인하고, parent children도 다시 읽어 승인 목록과 매핑한다. parent에는 기존 본문을 보존한 공유 가능한 description section 또는 comment로 child key·목표·AC·dependency mapping과 상세 계획 canonical 위치를 승인 범위 안에서 기록하고 readback한다. 이 검증 또는 공유가 불완전하면 구현 준비 완료가 아니다.

## 위임 계약

위임 경로에서는 상세 API·ENUM·schema 계획이나 하위 태스크를 강요하거나 자동 생성하지 않는다. story에는 수임자가 상세 설계와 하위 태스크를 작성할 책임을 기록한다. 실제 수임자가 정해지지 않았다면 책임자는 `미정`으로 두고 임의 이름을 넣지 않는다.

Jira story 반영은 승인과 readback 뒤에만 한다. Jira 반영만 확인됐을 때 산출 상태는 `위임 준비` 또는 `Jira 반영 완료`다. `전달 완료`는 사용자가 실제 전달을 확인했거나, 명시 승인된 수임자·채널로 전달해 성공 근거를 확인한 경우에만 쓴다. 이는 개발 완료나 Done이 아니며, 하위 태스크가 없다는 이유로 미완료·차단으로 표시하지 않는다. 타인에게 메시지를 보내거나 assign하는 행동은 별도 외부 변경이므로 승인 없이 수행하지 않는다.

공통 권한·기록·완료 규칙은 [development-workflow.md](../../references/development-workflow.md)를 읽고 따른다.

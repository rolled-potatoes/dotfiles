# 보고서 품질 검사와 합성 회귀 사례

## 제출 전 검사

- 다섯 목차가 정확한 순서로 있고, 각 AC에 적어도 하나의 근거 기반 시나리오와 출처가 있는가?
- 정책의 적용 조건·예외, 명시된 범위 제외, 책임 경계가 빠지지 않았는가?
- 미결정 항목마다 결정 질문과 영향이 있으며, 충돌은 날짜·출처·내용과 함께 최신순으로 보이는가?
- 미결정 질문이 원문의 부족·충돌·미확정 또는 요구 해석에 필요한 빈칸에 근거하는가? 언급되지 않은 기능·필드·예외의 가능성만으로 질문을 만들지 않았는가?
- 각 미결정 질문이 다른 본문·댓글·스레드에서 이미 명시적으로 답변되었는지 확인했는가? 답변이 있으면 제거하고, 답변 자체가 충돌하면 충돌로 남겼는가?
- 원문이 제시하지 않은 개념·도메인을 질문의 선택지로 나열하지 않았는가? 원문 대안이 없으면 선택지 없이 중립적인 질문으로 썼는가?
- 기능상 연관성만으로 요구를 책임 도메인에 배정하지 않았는가? 귀속 근거 없는 요구는 AC에 보존하고 책임은 미결정으로 남겼는가?
- 각 주요 항목의 출처가 실제 원문 링크 또는 입력 위치인가? URL 매핑 없는 ID만 출처로 쓰지 않았는가?
- `확인되지 않음`과 조사 한계가 실제 미열람·접근 실패를 숨기지 않는가?
- 키워드 일치, 문서 수정일, 일반 관행, 분석자의 추론만으로 관계·정책·완료 조건을 확정하지 않았는가?
- 같은 근거와 결과를 반복하지 않고, 보고서만으로 사람이 다음 결정을 파악할 수 있는가?

## 합성 사례

아래 사례는 결과 문구를 외우기 위한 템플릿이 아니다. 스킬이 빠뜨리거나 만들어 내면 안 되는 정보를 점검하는 용도다.

1. **분산 자료**: Jira에는 완료 결과, Notion에는 예외 조건, Slack 스레드에는 적용 대상, Sheet에는 명시적 제외가 있다. 모든 자료의 관계가 확인되면 하나의 AC·정책·도메인 범위로 중복 없이 취합하고 각각 실제 원문 링크나 입력 위치를 출처로 남긴다. 취소 API 같은 구현 명칭을 독립 도메인으로 만들지 않고, 근거로 확인된 도메인 책임 아래에 배치한다. 기능 연관성만으로 API 반환 요구를 수강 도메인에 귀속하지 않으며, 귀속 근거가 없으면 AC로 보존하고 책임 경계를 미결정으로 둔다.
2. **순환·중복 참조**: Jira가 Notion을, Notion 댓글이 동일 Jira를, Slack이 동일 Notion URL을 참조한다. canonical ID와 문맥으로 한 번만 조사하며, 참조가 되돌아온다고 조사를 멈추지 않는다.
3. **날짜가 있는 충돌**: 이전 Slack 메시지는 A, 뒤의 Jira 댓글은 B를 말하지만 변경·폐기 선언은 없다. 최신 내용부터 충돌로 나열하고 B를 확정 정책으로 쓰지 않는다.
4. **접근 실패**: 연결 문서가 권한 오류이고 첨부 읽기 도구도 없다. 그 문서의 내용을 추정하지 않고 5절에 자료와 실패 범위를 적는다.
5. **불충분한 요구**: “알림을 개선”만 있고 대상·기대 결과·책임이 없다. 화면·API를 독립 도메인으로 만들거나 임의 AC·범위를 만들지 않고, 필요한 결정 질문과 영향만 4절에 적는다. 확인된 도메인이 없으므로 3절에는 `확인되지 않음`으로 쓴다.

각 사례에서 관계 없는 동명 자료는 제외하고, 확인 가능한 자료의 URL 또는 입력 위치를 추적할 수 있어야 한다.

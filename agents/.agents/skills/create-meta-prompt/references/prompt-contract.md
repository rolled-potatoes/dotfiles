## 1. 작성 원칙

최종 산출물은 다른 Codex가 그대로 받아 본 작업을 수행하는 하나의 Markdown 문서다. 설명용 메타 분석과 작성 과정을 포함하지 않는다.

- 각 지시는 대상 Codex가 수행할 수 있는 행동과 완료 조건으로 쓴다.
- 확인된 사실, 사용자 결정과 허용된 가정만 포함한다.
- 목표에서 작업, 산출물, 검증, 완료 보고까지 추적 가능하게 연결한다.
- 반복되는 지시를 합치고 상위 지침을 장황하게 다시 쓰지 않는다.
- 모든 예시 표기와 안내 문구를 실제 내용으로 교체한다. 빈 항목은 절과 함께 제거한다.

## 2. 필수 구조

다음 순서와 의미를 유지한다. 작업 특성상 가까운 절을 합치더라도 항목 자체를 누락하지 않는다.

### 제목

`# Agent 작업 프롬프트`로 시작한다. 다음 문장에서 수행할 작업을 한 줄로 요약한다.

### 목표와 요청 유형

- 달성해야 할 결과를 명시한다.
- 답변·설명·검토·보고, 진단, 변경·구축, 자동화·모니터링 중 요청 유형을 명시한다.
- 독자나 결과 사용자가 작업 결과를 바꿀 때만 함께 명시한다.

### 배경과 현재 상태

- 해결할 문제와 지금 상태를 근거에 맞게 설명한다.
- 이전 결정이나 기존 동작 중 대상 Codex가 알아야 할 내용만 포함한다.
- 사실과 판단을 섞지 않는다.

### 성공 기준

- 작업이 완료됐다고 판정할 관찰 가능한 조건을 작성한다.
- 각 조건을 검증 또는 산출물과 연결한다.
- “잘 동작한다”, “품질을 높인다”처럼 판정할 수 없는 표현은 사용하지 않는다.

### 근거

- 관련 파일과 줄, 문서, URL, 버전, 명령 결과 등 다시 확인할 수 있는 위치를 기록한다.
- 근거가 적용되는 주장이나 작업 단계가 무엇인지 함께 밝힌다.
- 현재성이 중요한 근거에는 확인 기준 시점을 포함한다.

### 확정 결정

- 사용자가 선택한 제품 동작, 우선순위, 기술 선택과 정책을 기록한다.
- 조사로 확인한 기존 계약을 사용자 결정인 것처럼 쓰지 않는다.
- 선택되지 않은 대안이나 결정 과정을 장황하게 남기지 않는다.
- 사용자가 정하지 않은 공개 동작, 지원하지 않는 입력의 처리, 오류 정책과 추가 산출물을 결정으로 만들지 않는다.

### 범위와 권한

- 포함 범위와 제외 범위를 구분한다.
- 읽기, 파일 변경, 테스트, 외부 쓰기, 삭제, 배포, 메시지 발송 등 허용된 행동을 명시한다.
- 기존 사용자 변경, 비밀정보와 관련 없는 시스템을 보존하도록 한다.
- 위험하거나 복구하기 어려운 작업에는 사용자 확인이 필요한 정확한 시점을 명시한다.
- 외부·파괴적 작업에는 정확한 대상, 선택·제외 기준, 기간·보존 범위, 후보 검토, 최종 승인, 복구 가능성, 부분 실패 정책과 성공 확인을 포함한다.
- 현재 디렉터리나 로그인 상태만으로 외부 작업 대상을 추론하지 않는다.

### 실행 지침

- 대상 Codex가 따라야 할 작업 흐름을 의존 순서대로 작성한다.
- 조사와 구현, 검증을 구분하되 자명한 명령까지 세분화하지 않는다.
- 저장소의 `AGENTS.md`, 기존 구조와 적용 가능한 설치 스킬을 먼저 따르게 한다.
- 구현 중 새 제품 결정이 필요한 모순을 발견하면 임의로 결정하지 말고 근거와 선택지를 보고하게 한다.
- 기존 구조 안의 가역적인 코드 수준 선택은 대상 Codex가 맡게 하되 사용자 경험, 호환성, 데이터와 권한을 바꾸는 선택은 맡기지 않는다.

### 산출물

- 생성하거나 변경할 결과와 필요한 형식을 명시한다.
- 파일 경로는 확인됐거나 사용자가 정한 경우에만 고정한다.
- 결과에 포함할 필수 내용과 포함하지 않을 내용을 명시한다.
- 진단에 수정 권고, 조사에 실행 계획처럼 요청 유형을 넘어서는 결과를 관행적으로 추가하지 않는다.

### 검증

- 성공 기준을 증명하는 검사, 테스트 또는 관찰 방법을 작성한다.
- 기존 저장소에서 확인한 명령은 정확히 기록한다.
- 확인하지 못한 명령이나 테스트 이름을 만들어 내지 않는다.
- 실행할 수 없는 검증은 통과로 간주하지 말고 제한과 남은 위험을 보고하게 한다.

### 완료 보고

- 결과를 먼저 요약하게 한다.
- 변경한 대상, 실행한 검증과 결과, 확인하지 못한 항목, 남은 사용자 결정을 구분하게 한다.
- 커밋, push, 배포 또는 외부 전송은 명시적으로 요청됐을 때만 완료 보고 대상에 포함한다.

### 실행 체크리스트

대상 Codex가 완료 전에 확인할 작업별 체크 항목을 넣는다. [실행 체크리스트](#4-실행-체크리스트)의 기준을 따른다.

### 평가 기준

작업 결과의 통과 조건과 증거를 표로 작성한다. [평가 기준](#5-평가-기준)의 기준을 따른다.

## 3. 선택 구조

다음 절은 실제 위험이나 성공 기준에 필요할 때만 추가한다.

- **오류와 경계 조건**: 실패, 부분 성공, 빈 값, 중복, 동시성 등 처리 결정이 있는 경우
- **API와 I/O**: 요청·응답, 이벤트, 파일 형식 또는 공개 인터페이스가 바뀌는 경우
- **데이터와 마이그레이션**: 스키마, 변환, 호환성 또는 복구가 필요한 경우
- **보안과 개인정보**: 인증, 권한, 비밀정보, 개인정보 또는 공개 범위가 관련된 경우
- **성능과 용량**: 측정 가능한 목표나 기존 병목 근거가 있는 경우
- **외부 시스템**: 계정, 연결, 승인, rate limit 또는 외부 쓰기가 필요한 경우
- **배포·롤백·모니터링**: 운영 반영이나 지속 관찰이 작업 범위에 포함된 경우

선택 구조에 넣을 결정이나 근거가 없다면 일반적인 모범 사례로 내용을 채우지 않는다.

## 4. 실행 체크리스트

체크리스트는 작업 순서와 완료 판단에 필요한 항목만 포함한다.

- 각 항목은 대상 Codex가 직접 확인할 수 있는 행동으로 작성한다.
- 성공 기준과 검증에서 다루지 않는 새 요구사항을 추가하지 않는다.
- “코드 품질 확인” 대신 무엇을 어떤 근거로 확인할지 적는다.
- 위험한 작업은 실행 전 확인과 실행 후 성공 확인을 별도 항목으로 둔다.
- 검증하지 못한 항목을 완료 표시하지 않도록 지시한다.

## 5. 평가 기준

평가 기준은 점수보다 통과 여부와 증거를 우선한다. 다음 열을 사용하는 표로 작성한다.

| 평가 항목 | 통과 조건 | 확인 근거 |
| --- | --- | --- |
| 작업별 핵심 결과 | 성공 기준을 충족하는 관찰 가능한 상태 | 테스트, 파일, 출력 또는 공식 출처 |

작업에 맞는 평가 항목을 추가하되 다음 원칙을 지킨다.

- 모든 성공 기준이 최소 하나의 평가 항목에 연결돼야 한다.
- 통과 조건은 대상 Codex가 임의로 해석하지 않아도 판정 가능해야 한다.
- 확인 근거에는 실행할 검사나 확인할 산출물을 지정한다.
- 사용자 취향이나 제품 결정을 평가 모델의 추측으로 대체하지 않는다.
- 하나라도 필수 조건을 증명하지 못하면 전체 통과로 보고하지 않는다.

## 6. 전달 전 품질 게이트

생성한 프롬프트가 다음 조건을 모두 만족할 때만 전달한다.

### 구체성

- 목표와 모든 성공 기준이 관찰 가능하고 검증 가능하다.
- `적절히`, `필요하면`, `등`, `최선의 방식`처럼 결정을 떠넘기는 표현이 핵심 지시에 남아 있지 않다.

### 결정 완결성

- 결과를 바꾸는 모호성이나 상충하는 지시가 없다.
- 대상 Codex가 제품 동작, 정책 우선순위 또는 중요한 기술 선택을 새로 결정할 필요가 없다.
- 대상 Codex가 맡아도 되는 가역적인 구현 선택까지 불필요하게 고정하지 않았다.

### 근거성

- 구체적인 현재 상태, 경로, 버전, 인터페이스와 정책을 입력 또는 조사 근거로 추적할 수 있다.
- 확인하지 못한 내용을 사실, 결정 또는 금지 규칙으로 만들지 않았다.

### 범위와 권한

- 포함 범위, 제외 범위와 허용된 변경이 구분된다.
- 외부 쓰기와 복구하기 어려운 작업의 대상, 확인 조건과 성공 확인이 명확하다.
- `모두`, 상태 이름, 기간, 제외 조건, 백업과 부분 실패 동작이 사용자 결정 없이 해석되지 않았다.

### 실행 가능성

- 실행 순서, 산출물과 중단 조건이 서로 모순되지 않는다.
- 필요한 파일, 도구, 스킬 또는 외부 접근을 실제로 사용할 수 있는지 확인했다.

### 검증 가능성

- 각 성공 기준을 증명할 검사 또는 관찰 방법이 있다.
- 완료 보고가 실행한 검증과 남은 위험을 숨기지 않도록 요구한다.

### 산출물 무결성

- TODO, 빈 placeholder, 선택되지 않은 대안과 불필요한 빈 절이 없다.
- 본 작업을 이미 수행했다고 오해할 표현이나 작성 과정의 메타 설명이 없다.

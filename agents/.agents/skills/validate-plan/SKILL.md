# Validate Plan

확정된 개발 계획의 사실성과 실행 가능성을 검증한다. 검증 중에는 제품 코드를 구현하지 않는다.

## 원칙

- 사실, 추론, 미검증 항목을 명확히 구분한다.
- 라이브러리와 API는 계획이 사용할 정확한 버전을 기준으로 검증한다.
- 외부 기술 주장은 공식 문서, 공식 릴리스 노트, 표준 문서, 원본 저장소 등 1차 자료를 우선한다.
- 문서에 존재한다는 사실만 확인하지 말고 현재 저장소의 런타임, 의존성, 설정과 함께 동작하는지 확인한다.
- 검색 결과 요약이나 블로그만으로 핵심 주장을 확정하지 않는다.
- 검증을 위해 제품 코드, lockfile, 데이터, 외부 시스템을 변경하지 않는다.

## 검증 절차

### 1. 계획과 기준 고정

1. 대화에서 가장 최근에 확정된 계획, 요구사항, 성공 조건을 찾는다.
2. 계획이 없거나 여러 버전 중 무엇이 최종안인지 식별할 수 없을 때만 사용자에게 계획을 요청한다.
3. 계획의 각 단계를 독립적으로 검증 가능한 주장으로 분해한다.

다음 유형을 빠뜨리지 않는다.

- 저장소 구조와 기존 코드에 관한 주장
- 라이브러리, API, 옵션, 명령, 타입에 관한 주장
- 런타임 및 의존성 버전 호환성
- 컴포넌트 사이의 통합 방식과 데이터 흐름
- 마이그레이션, 오류 처리, 보안, 성능, 배포와 롤백 전제
- 테스트가 실제 위험과 성공 조건을 증명하는지 여부

### 2. 로컬 근거 수집

저장소 지침, 관련 구현, manifest와 lockfile, 설정, 스키마, 테스트, CI를 확인한다. 작업 트리가 더러우면 사용자 변경을 보존한다.

각 주장에 다음을 기록한다.

- 위험도: `critical`, `high`, `medium`, `low`
- 상태: `verified`, `contradicted`, `unverified`
- 근거: 로컬 파일과 줄, 실행 결과, 또는 공식 출처
- 영향: 틀렸을 때 실패하는 계획 단계

### 3. 외부 스펙 검증

외부 정보가 필요하면 인터넷을 검색한다. 현재 정보가 바뀔 수 있는 내용은 반드시 최신 자료로 확인한다.

1. 저장소가 사용하는 버전 또는 계획에서 제안한 버전을 식별한다.
2. 공식 문서에서 기능, 시그니처, 옵션, 제약 조건을 확인한다.
3. 공식 릴리스 노트나 원본 저장소에서 도입 버전, 폐기 여부, 알려진 제한을 확인한다.
4. 런타임, peer dependency, 플랫폼과 라이선스 제약을 확인한다.
5. 근거 링크와 적용 버전을 기록한다.

공식 자료로 확인되지 않는 주장은 `verified`로 표시하지 않는다. 문서와 실제 패키지 동작이 충돌하면 그 차이를 명시한다.

### 4. 최소 실험 수행

문서만으로 확정할 수 없는 `critical` 또는 `high` 위험 주장에만 최소 실험을 수행한다.

- 가능하면 현재 저장소에 이미 설치된 정확한 버전을 사용한다.
- 임시 디렉터리 또는 기존 테스트 체계에서 최소 재현 코드를 실행한다.
- 컴파일, 타입 검사, API 호출 형태, 직렬화, 경계 조건처럼 해당 주장 하나만 검증한다.
- 새 의존성 설치, 네트워크 쓰기, 외부 시스템 변경, 비밀정보 사용이 필요하면 먼저 승인을 받는다.
- 생성한 임시 산출물을 정리하고 제품 코드에는 실험 코드를 남기지 않는다.

실험할 수 없다는 이유만으로 통과시키지 말고 `unverified`와 남은 위험을 기록한다.

### 5. 계획 전체 검토

개별 API가 존재하는지뿐 아니라 순서와 결합이 타당한지 확인한다.

- 누락된 선행 작업과 암묵적 전제
- 기존 아키텍처 및 규칙과의 충돌
- 실패 및 부분 성공 시의 일관성
- 관찰 가능성, 테스트 가능성, 롤백 가능성
- 성공 조건을 만족하지 못하는 구현 단계

문제가 발견되면 최소 변경으로 계획을 수정한다. 요구 범위를 임의로 넓히지 않는다.

## 판정 기준

- `PASS`: 모든 `critical`/`high` 주장이 근거로 확인되었고 구현을 막는 모순이 없다.
- `REVISE`: 실행 가능한 수정안이 있지만 원래 계획의 단계, 기술 선택, 또는 전제가 바뀌어야 한다.
- `BLOCKED`: 핵심 요구가 현재 방식으로 불가능하거나, 안전하게 결정하기 위한 정보 또는 권한이 없다.

`critical` 또는 `high` 항목이 `unverified`인 상태에서는 `PASS`를 주지 않는다.

## 결과 형식

다음 순서로 간결하게 보고한다.

1. **판정**: `PASS`, `REVISE`, `BLOCKED`와 한 문장 근거
2. **검증표**: 계획 단계/주장, 위험도, 상태, 핵심 근거
3. **발견 사항**: 모순, 누락, 버전 또는 통합 위험을 영향도 순으로 정리
4. **검증된 실행 계획**: 원안 유지 또는 수정된 전체 계획
5. **미해결 항목**: 구현 전에 사용자가 결정하거나 추가 검증할 내용

웹 자료는 주장 바로 옆에 링크하고, 로컬 근거는 파일 경로와 줄 번호를 제시한다. 실패한 명령도 관련 판정 근거로 요약한다. 검증 결과만 전달하고 구현은 시작하지 않는다.

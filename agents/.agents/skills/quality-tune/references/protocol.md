# 튜닝 운영 규칙

## 책임과 입력

메인은 사용자 소통·검토자 호출·최종 보고, 조정자는 연구·토론·채택·인계, 전문가들은 연구·논박·의도 확인, 전담 구현자 한 명은 대상 결과물의 수정을 맡는다. 조정자가 기록을 단독 편집하고 다른 참여자는 결과를 메시지로 반환한다. 기존 검토자는 제품 코드와 기록을 수정하지 않고 독립 검토한다.

조정자와 모든 참여자에게 이 문서의 절대 경로를 전달하고 읽게 한다. 실행 문맥 없이 역할만 호출된 경우 범위·원천 자료·기준 결과물·기록 경로를 요청하며 독자적인 튜닝을 시작하지 않는다. 동작 제약은 역할 지침이며 별도의 읽기 전용 샌드박스가 생긴다고 주장하지 않는다.

역할 파일에 지정된 모델과 추론 수준을 사용한다. 요청 모델·추론 수준을 사용할 수 없으면 이유와 영향을 보고하고 임의로 대체하지 않는다. 실행 중 확인된 모델과 설정값을 구분하여 기록한다.

등록된 역할 이름의 생성이 런타임에서 거부될 수 있다. 이 경우 오류를 알리고, 해당 TOML의 developer_instructions·model·model_reasoning_effort를 명시적으로 적용한 별도 일반 하위 에이전트를 생성할 수 있다. 각 역할에 독립된 에이전트를 유지하고 원본 역할 경로·요청 설정·실제 생성 방식을 기록한다. 추가 기능 제한 등 역할 파일의 필수 설정을 동등하게 적용할 수 없거나 모델·추론 수준을 지정할 수 없으면 중단하고 필요한 조건을 보고한다. 이 방식을 등록 이름 호출 성공으로 보고하지 않으며 권한 제한이나 승인 거부를 우회하는 데 사용하지 않는다.

공통 입력은 다음과 같다.

- 실제 작업 프로젝트와 큰 작업 디렉터리의 절대 경로
- 원천 요구사항·승인 범위·유지할 계약·개선 목표와 판단 방법
- 기준 커밋·파일·현재 변경 상태와 기존 검증 결과, 알려진 문제
- 업무 용어와 책임 경계: 확인된 의미와 미확정 해석 구분
- 사용자 지정 시간·비용 한도와 참여 전문가

기존 변경이 있는 작업 트리는 HEAD만으로 기준을 표현하지 않는다. 관련 시작 diff나 사본을 남겨 사용자 변경과 튜닝 변경을 구분한다. 입력을 보존하는 데 커밋이나 작업 트리 정리를 요구하지 않는다. 초기 구현자의 설명과 실제 원천 자료를 구분한다.

## 참여자 선정과 독립 연구

| 역할 | 참여 조건 |
|---|---|
| tuning_fowler | 공통: 변경 용이성과 점진적 개선 |
| tuning_ousterhout | 공통: 복잡도와 추상화의 질 |
| tuning_evans | 공통: 업무 언어와 책임 경계 |
| tuning_kleppmann | 데이터 정합성·트랜잭션·동시 실행·재시도·메시지·외부 연동 실패가 주요 쟁점 |
| tuning_gregg | 응답 시간·처리량·CPU·메모리·I/O 등 성능이 주요 쟁점 |

조정자는 작업별 전문가가 답할 질문과 참여 이유를 기록한다. 새 쟁점으로 추가 호출할 수 있으나, 부족한 전문성을 임의로 있다고 간주하거나 새 상시 역할을 자동 설치하지 않는다.

Evans 관점에서 필요한 용어와 책임을 먼저 정리하되 다른 전문가도 수정할 수 있다. 기존 용어가 충분하면 유지하고 문맥별 차이를 억지로 통일하지 않는다. 용어 합의를 설계 결론의 사전 합의로 사용하지 않는다.

전문가의 최초 연구는 다른 전문가의 결론·초기 구현자의 설계 변호·이전 토론을 상속하지 않는 별도 문맥에서 시작한다. 원천 자료, 중립적인 설명, 공통 용어, 기준 결과물은 공유한다. 런타임에서 가능한 경우 전체 대화 상속을 끄고 필요한 입력을 명시적으로 전달한다. 각 전문가는 직접 코드와 근거를 조사한다.

전문가들은 대상 코드·테스트·설정·문서·공유 기록을 수정하지 않는다. 상태를 바꾸는 실험이나 검사 산출물 충돌 가능성이 있으면 조정자·구현자와 실행 순서를 조율한다. 프로토타입이 필요하면 구현자가 격리된 실험 범위에서 작성한다. 버전 관리가 필요한 명령은 mise를 경유한다.

## 제안과 토론

개선안별로 다음 다섯 항목을 반환한다. 제안 수를 강제하지 않으며 개선이 없으면 살펴본 범위와 유지 이유를 남긴다.

1. 문제·기회: 발생 상황과 비용 또는 영향
2. 근거: 요구사항, 코드 위치, 조사·실험 결과
3. 대안: 현재 유지안을 포함한 비교
4. 효과·대가: 기대 효과, 추가 복잡도·변경 비용·부작용
5. 판단 변경 조건: 필요한 확인, 불리해지는 상황, 수정·철회할 근거

확인된 결함·위험 가설·개선 제안·판단 보류를 구분한다. 실제 인물의 공개된 원칙을 참고하되 사적 견해나 본인의 발언을 만들어내지 않는다. 원칙의 적용보다 승인된 요구사항과 실제 증거를 우선한다.

최초 상호 논박은 쟁점별 한 차례이며 반론과 답변이 정리되는 단위를 뜻한다. 채택 여부를 바꿀 새 근거를 얻을 구체적인 방법이 있으면 보완·재논박을 한 차례 추가한다. 사용자 요청과 지정 한도는 우선한다. 같은 주장이 반복되면 결정하고, 근거를 얻을 수 없으면 보류한다.

의미 차이는 원천 문서·업무 사례, 사실·예측 차이는 조사·실험, 우선순위 차이는 합의한 작업 목표로 해결한다. 각 반론에도 철회할 증거를 명시한다. 근거가 부족한 업무 정책을 전문가 합의만으로 확정하지 않는다.

조정자는 범위·제약 준수, 개선 근거, 비용·부작용, 확인 가능성 순서로 판단한다. 다수결을 사용하지 않으며 각 반론의 반영·반박·보류 이유를 남긴다. 요구사항 위반과 미해결 안전 문제를 소수 의견으로 치부하지 않는다. 범위 밖 개선은 별도 제안으로 남긴다.

결정은 채택·기각·보류로 남기고 변경 시 이전 이유와 새 증거를 연결한다. 현재 유지도 유효한 결정이다. 기존 검증에서 놓친 실제 결함은 선택적 튜닝 제안과 구분하여 수정·검증 경로로 보낸다. 결정 기록은 검증 결과가 아니다.

## 구현과 의도 확인

조정자는 채택한 결정의 목적·범위·유지 조건·대표 사례·확인 방법을 전담 구현자 한 명에게 전달한다. 다른 사용자나 세션의 변경을 보존하게 하고, 같은 대상 결과물에 추가 구현자를 두지 않는다.

주요 책임·계약 변경은 구현자가 무엇을 어떻게 바꿀지 설명하고 관련 전문가가 의도를 확인한다. 사소한 구현 선택까지 사전 확인하지 않는다. 서로 의존하는 변경은 작은 단위로 순차 구현하고, 주요 반론을 제기했던 전문가에게 실제 변경의 의도 반영을 확인받는다.

의도 확인 결과는 다음 중 하나다.

- 의도 반영 완료
- 합의 조건 미충족: 해당 조건·사례·근거 명시
- 새로운 개선 제안: 기존 결함과 구분하여 조정자에게 전달

검토 중 떠오른 선호를 기존 변경의 필수 수정으로 바꾸지 않는다. 구현자가 새 책임·정책·계약이 필요하다고 판단하면 조정자에게 돌려보낸다. 같은 조건을 반복해서 충족하지 못하면 의도 전달과 설계 전제를 재검토한다.

구현자는 승인된 필요한 검사를 수행하고 결과를 반환한다. 검사 실행 주체나 권한이 별도로 정해져 있으면 존중하고, 미수행을 통과로 기록하지 않는다. 조정자와 전문가의 의도 확인은 최종 검증을 대신하지 않는다.

## 독립 검증·재작업·종료

메인은 조정자의 인계를 받아 동일한 최종 결과물을 기존 policy_reviewer·test_reviewer·code_reviewer 및 조건부 reliability_reviewer에 전달한다. 원천 요구사항, 기준 diff, 채택 근거, 수행 검사, 이견·미확인 사항을 제공한다. 검토자는 자신에게 필요한 검사 항목을 독립적으로 판단한다.

| 검토 결과 | 후속 처리 |
|---|---|
| 구현 오류·회귀 | 조정자를 거쳐 같은 구현자가 수정 후 재검증 |
| 설계 전제·책임 오류 | 조정자와 관련 전문가가 해당 결정 재논의 |
| 개선 효과 미확인 | 제안 전문가와 조정자가 측정 조건·대안·유지 여부 재평가 |
| 환경·정보 부족 | 미검증 상태와 필요한 조건 명시 |
| 기존 결함 발견 | 선택적 개선과 구분하고 승인 범위·담당·검증 정리 |

기존 검토 체계의 재작업 한도를 유지한다. 철회할 경우 자기 튜닝 변경과 의존성만 확인하여 처리하며 사용자 변경을 덮거나 광범위하게 초기화하지 않는다. 요구사항이나 검증 기준을 통과 목적으로 낮추지 않는다.

최종 상태:

- 개선 완료: 반영된 변경의 의도 확인과 필요한 독립 검증 통과
- 변경 없이 종료: 대안보다 현재 유지가 적절하고 기준 결과물이 그대로임을 확인
- 일부 개선 완료·일부 보류: 반영된 변경은 검증 통과, 나머지 보류 이유 명시
- 진행 중단·판단 필요: 미해결 실패·정보·권한·환경 부족 또는 범위 밖 결정. 남은 diff·검증 상태·재개 조건 명시

사용자 지정 시간·토큰 한도를 지킨다. 지정하지 않은 시간·비용의 고정 한도는 만들지 않고 시범 운영에서 관찰한다. 실제 제공되는 사용량만 보고한다. 한도 도달이나 에이전트 종료를 성공으로 표시하지 않는다. 자동 재진입하지 않는다.

## 기록

튜닝은 큰 작업의 하위 단계다. 메인이 식별한 `<프로젝트 루트>/development/<task dir>/tune/<실행ID>/`를 사용한다. 현재 큰 작업을 식별할 수 없으면 사용자에게 경로를 확인하며 별도 quality-tune 작업 디렉터리를 임의로 만들지 않는다. 프로젝트 루트는 스킬 설치 위치가 아니라 실제 작업 루트다.

같은 실행은 기존 기록을 이어 쓰고 새 실행은 새 실행ID로 구분한다. 조정자가 다음 세 파일을 단독 관리한다. 다른 참여자의 결과는 메시지로 받아 반영한다.

| 파일 | 내용 |
|---|---|
| brief.md | 기준 버전과 시작 변경, 원천 자료, 승인 범위, 목표·제약, 기존 검증, 용어, 참여자·한도 |
| decisions.md | 제안·대안·근거·반론 처리·결정·변경 이유와 구현·검증 연결 |
| handoff.md | 현재 단계·실행ID·참여자 식별, 최종 diff, 의도 확인, 검사·독립 검토 결과, 미확인 사항·최종 상태·재개 조건 |

메인은 최종 검토 결과를 조정자에게 전달해 handoff.md에 반영시키고 저장 결과를 확인한다. 긴 원문 대화는 복제하지 않고 판단에 영향을 준 근거와 이견을 보존한다. 원천 요구사항은 링크로 연결하고 비밀값을 복사하지 않는다. Git ignore 정책이나 개발 역할을 자동 변경하지 않는다.

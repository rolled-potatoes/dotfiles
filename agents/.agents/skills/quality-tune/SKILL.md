# 개발 품질 튜닝

검증된 결과물의 품질을 개선하고 기존 검토 체계로 재검증한다. 전체 절차는 [운영 규칙](references/protocol.md)을 읽고 따른다. 전문가 원칙의 근거가 필요할 때 [출처](references/sources.md)를 읽는다.

## 시작과 위임

1. 대상 프로젝트와 큰 작업 디렉터리, 승인 범위, 개선 목적, 기준 결과물, 기존 검증 결과를 식별한다. 필수 실패가 남았거나 검증 결과를 확인할 수 없으면 튜닝을 시작하지 않고 필요한 조치를 알린다. 이미 승인된 범위는 다시 묻지 않는다.
2. 실제 제공되는 하위 에이전트 생성·메시지·대기 기능과 역할을 확인한다. 등록 이름으로 생성할 수 없으면 먼저 알리고 운영 규칙의 동등 설정 적용 조건을 확인한다. 하나의 에이전트가 여러 전문가를 연기해 독립 검토로 보고하지 않는다. 개인 동시 실행 한도는 변경하지 않는다.
3. 초기 구현자와 독립된 `tuning_coordinator`를 생성한다. 원천 자료와 기준 결과물, 목표·제약, 작업 디렉터리, 이 스킬과 운영 규칙의 절대 경로를 전달한다. 조정자의 요청에 따라 공통 전문가 3명과 필요한 작업별 전문가, 전담 구현자 1명을 연결한다.
4. 메인은 사용자 소통과 실행 지원을 맡고 튜닝 대상 코드를 수정하지 않는다. 조정자가 중첩 위임을 사용할 수 없으면 메인이 요청된 역할을 생성하고 결과를 전달한다. 전문가 선정·채택 판단은 조정자가 담당한다.

## 검증과 반환

조정자가 구현과 의도 확인 결과를 반환하면 메인이 동일한 최종 스냅샷을 `policy_reviewer`, `test_reviewer`, `code_reviewer`에 전달한다. 동시성·데이터 변경·외부 연동 위험이 있으면 `reliability_reviewer`도 호출한다. 기존 역할 지침과 재작업 한도를 유지한다.

필수 수정은 조정자에게 반환하여 같은 전담 구현자가 처리하게 한다. 관련 검토자에게 새 변경을 재검증받는다. 토론 합의·의도 확인·에이전트 종료를 최종 검증 통과로 간주하지 않는다.

메인은 최종 상태, 결과물과 기록 위치, 반영된 개선, 실제 검증 결과, 보류·이견·미검증 사항을 보고한다. 한 번의 호출은 한 차례의 튜닝으로 끝내며 자동 재진입하지 않는다. 커밋·push·PR·외부 변경은 기존 승인 절차를 따른다.

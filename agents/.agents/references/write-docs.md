# 한국어 사람 대상 문서 작성 지침

사람이 번역하거나 구조를 다시 해석하지 않아도 목적과 결론을 파악할 수 있는 문서를 작성한다.

## 규칙의 우선순위

1. 사용자의 명시적 지시를 따른다.
2. 조직·저장소의 기존 템플릿과 용어를 따른다.
3. 함께 호출된 PR, DDD, 회의록 등 전문 스킬의 필수 구조와 내용을 따른다.
4. 위 규칙과 충돌하지 않는 범위에서 이 지침의 가독성 기준을 적용한다.

기존 템플릿의 섹션을 임의로 추가·삭제하거나 이름을 바꾸지 않는다. 템플릿이 없을 때만 독자와 목적에 맞는 최소 구조를 만든다.

## 작성 전 확인

1. 문서의 독자, 읽은 뒤 기대하는 행동, 공유 매체를 확인한다.
2. 저장소나 입력 자료에서 기존 템플릿, 비슷한 문서, glossary, 자주 쓰는 표현을 찾는다.
3. 확인된 사실, 결정, 제안, 미결 사항을 구분한다.
4. 자료로 확인할 수 없는 내용은 채워 넣지 말고 가정이나 미결 사항으로 표시한다.

모든 구체적인 주장과 설계 세부사항을 입력 자료나 확인한 근거로 추적할 수 있게 한다. 일반적인 관행이라는 이유로 데이터 구조, 상태, 재시도, 보안, 단계적 배포의 세부사항을 추가하지 않는다. 사용자가 대안이나 설계를 요청했을 때만 필요한 최소 제안을 `제안`으로 분리하고, 그 밖의 미확정 세부사항은 짧은 미결 사항으로 남긴다.

- 미결 질문에 임시 기본값이나 금지 규칙을 만들어 답하지 않는다.
- 담당자, 승인 절차, 검증 단계, 예외 처리 방식을 근거 없이 배정하지 않는다.
- 요구된 안내 의미를 실제 확정 문구처럼 인용하지 않는다. 문구가 제공되지 않았다면 의미 수준으로 기록하거나 `문구 예시`라고 표시한다.

독자나 목적을 알 수 없더라도 결과를 크게 바꾸지 않으면 가장 가까운 기존 문서 관례를 사용하고 계속한다. 중요한 의미가 달라질 때만 사용자에게 묻는다.

## 구성

- 제목과 첫 문단에서 문서의 목적 또는 핵심 결론을 전달한다.
- 결정, 핵심 변경, 요청 사항, 다음 행동처럼 독자가 먼저 알아야 할 내용을 세부 근거보다 앞에 둔다.
- 배경, 문제 정의, 달성 목표를 설명할 수 있는 문서에는 해당 내용을 반드시 포함한다.
- 내용이 없거나 문서 목적과 무관한 섹션을 형식 때문에 만들지 않는다.
- 사실과 판단 근거를 결론 뒤에 배치하고, 미결 사항과 다음 행동을 명확히 분리한다.

문서 종류에 따라 첫 부분을 다음처럼 조정한다.

- 계획·정책·설계 문서: 목표 또는 결정 → 문제와 배경 → 실행 내용과 영향
- 회의록: 결론과 결정 → 할 일과 담당 → 주요 논의와 미결 사항
- PR: 작업 요약 → 문제 정의 → 변경 내용 → 영향과 리뷰 지점
- 결과 보고: 결과와 판정 → 핵심 근거 → 영향과 후속 작업

전문 스킬이나 기존 템플릿이 다른 순서를 요구하면 그 순서를 우선한다.

## 언어와 용어

- 조직에서 실제로 쓰는 한국어와 확정된 domain language를 우선한다.
- 쉬운 한국어로 의미가 충분하면 장식적인 비즈니스 용어나 영어 표현을 쓰지 않는다.
- 직역투와 번역이 필요한 어색한 영어를 자연스러운 한국어로 바꾼다.
- 코드 식별자, API, event, type, policy 이름과 공식 domain term처럼 정확성이 필요한 canonical English는 보존한다.
- 입력에 영어로 적혀 있다는 이유만으로 canonical term으로 간주하지 않는다. glossary, 기존 문서, code 표기 또는 공식 명칭에서 보존 근거를 확인한다.
- 보존 근거가 없는 `business-critical`, `ASAP`, `unit test`, `rollout` 같은 일반 표현은 각각 `업무상 중요`, `가능한 빨리`, `단위 테스트`, `단계적 배포`처럼 문맥에 맞는 한국어로 쓴다.
- 필요한 영어 용어는 첫 사용 시 한국어 설명을 함께 제공하고 이후 표현을 통일한다.
- 같은 개념에 여러 용어를 섞지 않는다.

## 문장과 레이아웃

- 문단 첫 문장에 결론이나 요지를 둔다.
- 한 문단에는 하나의 주제만 담고, 긴 문단은 의미 단위로 나눈다.
- 병렬 정보, 절차, 조건, 할 일은 bullet list 또는 numbered list로 정리한다.
- 순서가 중요할 때만 numbered list를 사용한다.
- 둘 이상의 대안이나 대상을 같은 기준으로 비교할 때는 표를 우선 검토한다.
- 표의 열과 행을 억지로 채우지 말고, 비교 기준이 불명확하면 짧은 목록을 사용한다.
- 문서 상단에 작성자, 작성일, 수정일 같은 메타정보 표를 만들지 않는다.
- 이모지는 기본적으로 사용하지 않고, 매체나 사용자가 요구할 때만 최소한으로 사용한다.
- 장식용 제목, 반복 요약, 불필요한 안내 문구를 추가하지 않는다.

## 수정과 검토

기존 문서를 수정할 때는 의미, 필수 섹션, 링크, ID, code block을 보존한다. 구조 변경이 필요하면 독자의 이해를 실제로 개선하는 범위로 제한한다.

초안 뒤에 다음을 확인하고 바로 고친다.

- 첫 화면에서 목적, 결론, 요청 사항을 찾을 수 있는가
- 조직에서 쓰지 않는 용어나 불필요한 영어가 남아 있는가
- 문단이 결론 없이 길게 이어지는가
- 목록이나 표가 산문보다 비교·절차를 명확히 보여 주는가
- 배경, 문제, 목표 중 설명 가능한 핵심 맥락이 빠졌는가
- 빈 섹션이나 근거 없이 채운 내용이 있는가
- 사실, 제안, 결정, 미결 사항이 섞여 있는가
- 전문 스킬과 기존 템플릿의 계약을 보존했는가

Markdown 파일을 작성하거나 수정했다면 가능할 때 경량 검사를 실행한다.

```bash
python3 "$HOME/.agents/scripts/validate_docs.py" <markdown-file-or-directory> [...]
```

오류는 수정한 뒤 완료하고, 경고는 문서 목적에 비추어 검토한다. 경고가 타당한 예외라면 문서를 억지로 바꾸지 않는다.

## 결과 전달

- 작성·수정한 문서와 핵심 변경을 짧게 알린다.
- 확인하지 못한 사실, 사용한 가정, 남은 결정을 분리해 알린다.
- 검사기를 실행했다면 오류와 경고 처리 결과를 알린다.

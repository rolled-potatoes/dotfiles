# 개발 파일별 작성 규칙

개발 문서와 산출물은 전역 writing style을 따른다. 문제·작업·결정·코드·검증은 담당 파일에 기록하고 링크로 연결한다. 시각은 persistence.md의 KST 규칙을 따른다.

## 문서 구분

| 구분 | 역할 | 관리 방식 |
|---|---|---|
| 세션 기준 문서 | 현재 범위·진행·결정·검증 상태와 남은 작업 | 아래 6개 문서를 정해진 위치에서 갱신 |
| 과정 산출물 | 조사·초안·개별 검토·로그·스냅샷 등 상세 근거 | 필요할 때 artifacts/에 보존하고 기준 문서에서 연결 |
| 사용자 확인용 리포트 | 사용자가 요청한 작업의 결과·근거·남은 사항 | 파일로 제공할 때 reports/에 작성하고 session.md에서 안내 |

기준 문서는 역할과 위치가 고정된다. progress.md와 decisions.md의 진행·결정 이력은 유지하며, 상세 자료만 과정 산출물로 분리한다. 파일명·확장자보다 용도로 분류한다. 예를 들어 개별 검토 자료는 과정 산출물, 사용자에게 전달할 종합 검토 결과는 리포트다.

확정된 범위·결정·검증 결과는 담당 기준 문서에 반영한다. 현재 기준의 핵심 내용을 갱신하고 상세 근거를 연결하며, 오래된 본문에 최신 보고서 링크만 덧붙여 대체하지 않는다.

## session.md — 어떤 작업이며 어디까지 했는가

- 제목·역할·생성일, 기록용 ID와 확인 가능한 실제 세션 ID
- 간략한 현재 상태, 미결 사항과 다음 작업
- 범위·진행·결정·검증·외부 활동·선행 세션 링크
- 사용자 확인용 리포트의 대상 작업·기준 시점·링크와 현재 유효한 리포트 안내
- 마지막 갱신 시각

작업의 진입점으로 사용하며, 다른 파일의 본문과 긴 시계열 이력은 복사하지 않는다.

## scope.md — 무엇을 어떤 기준으로 구현하는가

- 해결할 문제 정의
- 포함 범위와 제외 범위
- 달성 조건: 목표·인수조건
- 전달된 명세·방향성 문서의 위치와 적용 기준
- 관련 티켓·저장소와 작업 시작 시 확인한 코드 기준
- 구현할 큰 작업 단위와 남은 확인 사항

인수조건은 검증 항목과 연결한다. 원본 ID를 우선 사용하고, 필요하면 `AC-001` 같은 ID를 부여한다. 근거·확정 내용·해석·변경 제안을 구분하며, 변경 이력은 decisions.md에 연결한다.

## progress.md — 어떤 큰 작업을 수행했고 결과는 무엇인가

Jira 에픽 아래 스토리·작업을 나누는 정도의 큰 단위로 기록한다. 이 기준은 Jira 이슈 생성·변경 지시가 아니다.

- 목적과 현재 상태
- 수행한 작업과 결과
- 관련 코드·결정·검증 링크
- 남은 일과 막힌 이유
- 순서가 중요한 시작·완료·중단·재개 시각

명령·파일 수정·테스트마다 항목을 만들지 않는다. 재개나 원인 이해에 필요한 부분만 상세화하고, 사용자 실행 대기와 코드 수정 중인 상태를 구분한다.

## decisions.md — 구현 중 무엇을 왜 선택했는가

- 결정 내용·ID와 확정·제안·보류·대체됨 상태
- 질문과 출발점, 대안·근거·선택 및 미채택 이유
- 구현상 선택인지 사용자 확인이 필요한 기획·동작 변경인지 구분
- 사용자 확인 근거
- 관련 인수조건·작업 단위·코드·검증과 반영 위치
- 확정·변경·번복 시각 및 이전 결정

의미 있는 판단이 생겼을 때 작성하며, 코드 편집마다 항목을 만들지 않는다. 파일 저장·에이전트 권고·침묵은 사용자 승인이 아니다.

## verification.md — 어떻게 완료를 판단하며 결과는 무엇인가

착수 전 사용자와 검증 방법을 논의한다. 계획과 사용자 수행 보고는 같은 검증 항목에 기록한다.

| 구분 | 기록 내용 |
|---|---|
| 계획 | 연결된 인수조건, 검증 대상·수단, 필요한 환경·전제, 통과 기준 |
| 결과 | 사용자 완료 보고, 보고한 수행 방법·환경·결과, 제공된 증거 |
| 후속 조치 | 보고된 실패·미충족 원인, 수정과 사용자 재검증 결과 |

- 검증 수단은 작업에 맞춰 논의한다. 자동 테스트·수동 확인·시각 확인을 모두 필수로 요구하지 않는다.
- 테스트·빌드·앱 실행은 사용자가 결정하고 수행한다. 에이전트는 실행 방법·목적·영향·판단 기준을 제시하고 보고를 기다린다.
- 완료 보고만 있으면 사용자 수행 완료로 기록한다. 통과·실패는 보고된 결과에 따라 기록하고, 없는 결과·증거를 추정하지 않는다. 별도 증빙·에이전트 재실행을 완료 조건으로 요구하지 않는다.
- 검증 계획 합의·변경과 결과·재검증 보고 시각은 persistence.md에 따라 기록한다. 실제 수행 시각과 보고 시각을 구분한다.
- 기준을 바꾸면 이유를 남기고, 중요한 통과 기준·인수조건 변경은 사용자 확인을 거친다.
- 미수행을 통과로 기록하지 않는다. 통과 보고 뒤 새 변경·실패·미해결 우려가 없으면 반복 실행을 요청하지 않는다.

## external-actions.md — 어떤 위험과 코드 외 활동이 남았는가

위험이나 필요한 외부 활동이 있을 때만 생성한다. 예: 스키마 마이그레이션, 환경변수 추가, 인프라 구축.

- 관련 작업·결정·변경과 연결된 필요 이유
- 위험·예상 영향·확인된 제약과 불확실성
- 필요한 활동과 선행 조건
- 수행·확인 상태, 완료·검증·인계에 미치는 영향
- 사용자 결정·수행 완료 보고와 순서가 중요한 상태 변화 시각

위험과 대응 행동을 구분한다. 담당자·일정·실행 순서는 확인된 내용만 적는다. 환경변수는 이름·용도·설정 대상을 적고 비밀값은 복사하지 않는다.

필요한 행동·이유·영향을 제시해 사용자 결정을 요청하고, 수행·완료 보고에 따라 갱신한다. 문서 기록을 외부 서비스·환경 변경 승인으로 간주하지 않는다. 일상적인 검증은 verification.md에만 기록한다.

## artifacts/ — 어떤 과정과 근거를 보존하는가

- 재개·추적·재현에 필요한 자료만 선택해 보존한다. 모든 작업마다 산출물 파일을 만들 필요는 없다.
- 조사 메모·계획 초안·개별 검토·도식·실행 로그·조회 결과·소스 사본 등을 작업별로 묶을 수 있다.
- 자료의 목적·대상·기준 시점을 식별하고 관련 기준 문서나 리포트에서 연결한다. 원본 로그처럼 설명을 넣기 어려운 자료는 연결하는 문서에서 설명한다.
- 과거 자료는 당시 기록으로 보존한다. 여기서 확정된 내용은 기준 문서에 반영하며, 산출물 저장 자체를 승인이나 현재 기준의 확정으로 보지 않는다.

## reports/ — 사용자가 요청한 작업의 결과는 무엇인가

- 사용자가 요청하거나 합의한 확인용 리포트를 파일로 제공할 때 사용한다. 모든 응답을 별도 파일로 저장하지 않는다.
- 결론부터 쓰고, 요청 범위·수행 결과·근거·미검증 및 남은 사항을 필요한 만큼 담는다. 고정 목차는 강제하지 않는다.
- 대상 작업과 기준 시점을 밝혀 리포트만 읽어도 결과를 이해할 수 있게 한다. 상세 과정·로그는 artifacts/ 등 실제 근거로 연결한다.
- 리포트는 해당 시점의 결과이며, 이후 상태는 기준 문서에서 관리한다. 후속 보고는 기존 보고와의 관계를 밝히고, 기존 보고를 정정하면 정정 이유와 시점을 남긴다.
- 리포트의 확정 내용과 기준 문서가 일치하는지 확인하고 session.md에 링크를 남긴다.

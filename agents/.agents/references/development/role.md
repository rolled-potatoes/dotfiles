# 개발 역할과 작업 흐름

문제·범위·인수조건에 따라 현재 구현을 조사하고 코드를 수정한다. 완료 기준을 먼저 논의하고, 사용자의 로컬 검증 보고에 따라 수정과 검증을 반복하며 기록한다.

## 시작과 입력

1. 현재 Codex 프로젝트의 기준 디렉터리를 확인하고 persistence.md에 따라 세션을 식별한다. 재개 시 디스크 기록을 먼저 읽는다.
2. 프로젝트 AGENTS.md와 관련 저장소의 작업 규칙·도메인 지식을 읽는다. 저장소 경로 등록은 도구 접근·외부 변경 승인이 아니다.
3. 문제·포함 및 제외 범위·목표·인수조건과 전달된 명세·방향성 문서를 scope.md에 정리한다.
4. 관련 티켓·명세에는 기존 작업 원천 규칙을 적용한다. 자료 형식을 일괄 강제하거나 없는 내용을 추정으로 확정하지 않는다.
5. 중요한 누락·충돌은 근거와 대안을 제시한다. 요구사항·동작·범위의 중요한 변경은 승인 후 확정한다.

## 수행 범위

- 현재 구현을 읽기 전용으로 조사하고, 승인된 범위에서 계획·코드 수정·기록을 수행한다.
- 요구사항 안의 구현 선택은 자율 진행하고, 중요한 판단은 근거와 함께 기록한다. 기획 변경은 제안으로 남기고 확정 전까지 기존 요구사항과 구분한다.
- 작업 기록은 큰 단위로 남기고, 재개에 필요한 부분만 상세화한다. 세션 기준 문서·선택적인 과정 산출물·사용자 확인용 리포트의 구분은 files.md를 따른다.
- 사용자 보고를 근거로 상태·결과를 기록한다. 직접 검증한 것으로 표시하거나 에이전트 재실행·추가 증빙을 요구하지 않는다.
- 커밋·push·PR·병합, 업무툴·공유 문서 변경, 배포·인프라 작업은 기존 승인 절차를 따른다. 역할 선택과 로컬 기록만으로 외부 자동화 권한을 얻지 않는다.

## 검증 계획과 반복

1. 문제·범위·인수조건과 큰 작업 단위를 정리한다.
2. 착수 전 인수조건별 검증 대상·수단·환경·통과 기준을 사용자와 논의해 verification.md에 남긴다. 계획에 필요한 읽기 전용 조사는 먼저 할 수 있다.
3. 승인된 범위에서 구현하고, 결과·중요한 판단·위험·필요한 외부 작업을 기록한다.
4. 검증의 실행 방법·목적·영향·판단 기준을 제시하고 사용자 수행 결정을 요청한다. 수행 보고를 기다리는 동안 독립적인 조사·문서 정리는 계속할 수 있다.
5. 사용자 보고를 검증 항목에 연결한다. 실패·미충족은 원인을 논의하고 수정한 뒤 사용자 재검증으로 이어간다.
6. 중요한 완료 조건·검증 기준 변경은 사용자 확인을 거친다. 실패를 통과로 만들기 위해 기준을 임의로 낮추지 않는다.
7. 확정된 범위·결정과 구현·검증 결과, 미해결 사항·외부 작업을 담당 기준 문서에 반영한다. 필요한 과정 자료는 artifacts/에 보존하고 연결한다.
8. session.md에 현재 상태·다음 작업을 갱신한다. 사용자 확인용 리포트를 파일로 제공할 때는 reports/에 작성하고, 기준 문서와의 일치를 확인한 뒤 session.md에서 연결한다.

검증 계획을 바꾸면 이유를 남긴다. 완료 보고만 있으면 사용자 수행 완료로 기록하고, 통과 결과나 증거를 추정하지 않는다. 통과 보고 뒤 새 변경·실패·미해결 우려가 없으면 같은 검증을 반복 요청하지 않는다.

## 완료와 인계

- 로컬 구현 완료, 사용자 보고에 따른 검증 상태, 외부 반영·병합 완료를 구분한다.
- 하위 태스크는 구현·검증 후, 상위 story/task는 실제 병합 확인 후 완료 후보가 된다. 상태명·전이 규칙은 실제 업무툴에서 확인한다.
- 남은 외부 작업·미검증 범위를 명시하고, 사용자 보고에 따른 결과는 출처를 밝힌다.
- 다른 세션이 기준 문서부터 읽고 이어갈 수 있도록 현재 상태·결정·검증 결과·남은 활동을 정리한다. 과거 산출물과 리포트는 기준 시점과 연결 관계를 남긴다.
- 최종 보고는 작업에 맞는 인계 형식으로 작성한다. 고정 목차를 강제하지 않는다.
